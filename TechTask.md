## На разработку микросервисной банковской системы «Mini Bank»

### 1. Общие сведения
**1.1. Название проекта:** Mini Bank (Микросервисная банковская система).  
**1.2. Назначение системы:** Система предназначена для управления банковскими счетами, обработки финансовых транзакций и обеспечения безопасных переводов между счетами с гарантией консистентности данных.  
**1.3. Целевая аудитория:** Внутренние пользователи (сотрудники банка) и внешние клиенты (через API).  
**1.4. Уровень проекта:** Production-ready / Enterprise (демонстрация компетенций Senior Go Developer).  

### 2. Цели и задачи проекта
*   Реализовать масштабируемую микросервисную архитектуру с принципом *database-per-service*.
*   Обеспечить строгую консистентность данных при распределенных транзакциях с использованием паттерна **Saga**.
*   Исключить состояние гонки (race conditions) при одновременном изменении баланса с помощью **пессимистичных блокировок**.
*   Внедрить полный цикл наблюдаемости (Observability) для мониторинга и трассировки распределенных запросов.
*   Автоматизировать процессы сборки, тестирования и развертывания (CI/CD).

### 3. Архитектура и состав микросервисов
Система строится по микросервисной архитектуре. Каждый сервис владеет своей базой данных. Внутреннее взаимодействие осуществляется по **gRPC**, внешнее — через REST API.

**3.1. API Gateway**
*   **Технология:** Go, Gin.
*   **Назначение:** Прием внешних HTTP/REST запросов, аутентификация/авторизация, валидация входных данных, маршрутизация и трансляция запросов во внутренние gRPC вызовы.

**3.2. Account Service (Сервис счетов)**
*   **Технология:** Go, gRPC, PostgreSQL.
*   **Назначение:** Управление жизненным циклом счетов (создание, блокировка, закрытие), хранение баланса.
*   **БД:** Выделенный инстанс PostgreSQL.

**3.3. Transaction Service (Сервис транзакций)**
*   **Технология:** Go, gRPC, PostgreSQL, RabbitMQ.
*   **Назначение:** Обработка переводов, реализация оркестрации/хореографии паттерна Saga, ведение журнала транзакций.
*   **БД:** Выделенный инстанс PostgreSQL.

**3.4 Веб клиент**
*   **Технология:** React
*   **Назначение:** Прототип позволяющий продемонстрировать работу бэкэнда

### 4. Функциональные требования
**4.1. Управление счетами (Account Service)**
*   Создание нового счета с уникальным идентификатором и начальным балансом.
*   Получение информации о счете и его текущем балансе.
*   Блокировка и разблокировка счета.

**4.2. Обработка транзакций (Transaction Service)**
*   Инициирование перевода средств между двумя счетами.
*   **Пессимистичная блокировка:** При списании средств использовать `SELECT ... FOR UPDATE` в PostgreSQL для блокировки строк счетов и предотвращения двойного списания (double-spending) и race conditions.
*   **Паттерн Saga (Оркестрация или Хореография):**
    *   *Шаг 1:* Резервирование средств на счете отправителя (статус `PENDING`).
    *   *Шаг 2:* Зачисление средств на счет получателя.
    *   *Шаг 3 (Коммит):* Подтверждение списания на счете отправителя.
    *   *Компенсирующие транзакции (Откат):* При ошибке на любом шаге (например, недостаточно средств, счет получателя заблокирован) выполнить откат предыдущих шагов (возврат резерва, отмена зачисления).
*   Генерация уникального `idempotency-key` для предотвращения дублирования транзакций.

**4.3. Асинхронные события**
*   Публикация событий об успешных/неуспешных транзакциях в **RabbitMQ** (например, для отправки уведомлений или обновления аналитики).

### 5. Нефункциональные требования
*   **Консистентность:** Данные должны быть согласованы в конечном счете (Eventual Consistency) за счет паттерна Saga.
*   **Идемпотентность:** Все финансовые операции должны быть идемпотентными. Повторный запрос с тем же `transaction_id` не должен менять баланс.
*   **Отказоустойчивость:** Сервисы должны корректно обрабатывать падения зависимостей (использование circuit breaker, retry с exponential backoff для gRPC).
*   **Безопасность:** Пароли/секреты не хранятся в коде. Использование TLS для gRPC.

### 6. Технологический стек
*   **Язык программирования:** Go 1.26.
*   **API:** gRPC (protobuf3) для межсервисного взаимодействия, REST (Gin) для внешнего API.
*   **Базы данных:** PostgreSQL 15+ (каждый сервис использует свою БД).
*   **Кэширование/Блокировки:** Redis (для кэширования справочников или распределенных блокировок, если требуется).
*   **Брокер сообщений:** RabbitMQ (для асинхронных событий и Saga).
*   **Наблюдаемость:** OpenTelemetry (сбор метрик и трейсов), Jaeger (трассировка), Prometheus (метрики), Grafana (визуализация).
*   **Инфраструктура:** Docker, Docker Compose.
*   **CI/CD:** GitHub Actions.

### 7. Требования к наблюдаемости (Observability)
*   **Трассировка (Tracing):** Интеграция OpenTelemetry SDK во все сервисы. Сквозная трассировка запроса от Gin (HTTP) через gRPC до PostgreSQL. Визуализация в Jaeger.
*   **Метрики (Metrics):** Экспорт метрик в Prometheus. Отслеживание:
    *   RPS (запросов в секунду) по каждому эндпоинту.
    *   Latency (время ответа) с разбивкой по перцентилям (p50, p95, p99).
    *   Количество ошибок (ошибки БД, gRPC таймауты, откаты Saga).
    *   Активные соединения с БД и RabbitMQ.
*   **Логирование:** Структурированные логи (JSON) с обязательным включением `trace_id` и `span_id` для корреляции с трейсами.

### 8. Инфраструктура и CI/CD
**8.1. Локальная разработка (Docker Compose)**
*   `docker-compose.yml` должен поднимать всю экосистему: все микросервисы, 2 инстанса PostgreSQL, Redis, RabbitMQ, Jaeger, Prometheus, Grafana.
*   Наличие скриптов (Makefile) для инициализации БД (миграции) и заполнения тестовыми данными (seed).

**8.2. CI/CD (GitHub Actions)**
*   **Триггеры:** Push в `main`, Pull Request в `main`.
*   **Этапы пайплайна:**
    1.  *Lint:* Проверка кода через `golangci-lint`.
    2.  *Test:* Запуск Unit-тестов. Интеграционные тесты с использованием `testcontainers-go` (поднятие временных БД в Docker).
    3.  *Build:* Сборка бинарных файлов и Docker-образов.
    4.  *Push:* (Опционально) Пуш образов в Docker Hub / GitHub Container Registry.

### 9. Требования к тестированию
*   **Unit-тесты:** Покрытие бизнес-логики (особенно математики транзакций и логики Saga).
*   **Интеграционные тесты:** Проверка взаимодействия сервиса с реальной БД и RabbitMQ.
*   **Нагрузочное тестирование (Опционально, но желательно):** Скрипт для `k6` или `vegeta`, проверяющий поведение системы при высоком concurrent RPS на один счет (демонстрация работы пессимистичных блокировок).

### 10. Критерии приемки (Definition of Done)
1.  Все микросервисы успешно поднимаются одной командой `docker-compose up`.
2.  Реализован сценарий перевода средств, при котором сбой на этапе зачисления корректно откатывает резервирование (работа Saga).
3.  При одновременном запросе перевода с одного счета (concurrency) баланс не уходит в минус, нет дедлоков БД.
4.  В Jaeger виден полный трейс прохождения HTTP-запроса через все сервисы и БД.
5.  В Grafana отображаются графики RPS, Latency и ошибок.
6.  GitHub Actions пайплайн успешно проходит все проверки при создании PR.
7.  Код покрыт тестами, проходит линтер, не имеет жестких зависимостей от внешних конфигураций (используются переменные окружения).
